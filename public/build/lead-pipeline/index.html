Lead → AI qualify → CRM + instant callback

An n8n workflow for home-service businesses. A lead hits a webhook; within seconds the owner's phone buzzes with a text they can act on, and the contact is already in the CRM, scored and tagged.

The point of the build is not that it calls an AI model. The point is that the lead never disappears — not when the model is down, not when the form is half empty, not when the phone number is garbage. Every path ends in a row somewhere.

Four design decisions worth defending

1. The AI writes the sentence. The code decides the routing.

The model proposes a score. src/qualify.js accepts it only if it lands within 25 points of a deterministic rule score computed from the same lead. Outside that window the two are averaged and the disagreement is recorded. The tier (A/B/C) is always recomputed from the final score — a model-supplied tier field is ignored even when it is present and even when it agrees. A prompt is a request; a clamp is a guarantee, and the owner's phone is wired to the clamp.

2. A lead is invalid only if we cannot reach the human.

No name, no message, no service, no city — all warnings. The one fatal condition is no usable phone and no usable email. A bare working phone number with nothing else attached is a real lead and is treated as one.

3. Nothing is thrown away silently.

The unreachable branch writes a row carrying the failure reason, so "we never heard from them" can be told apart from "we dropped it." Every lead that does get through also writes an audit row recording end-to-end latency and which engine produced the score — so a quiet degradation to the rule fallback is visible the next morning instead of a month later.

4. SMS and WhatsApp are two messages, not one message sent twice.

Both hang off the same tier-A gate as siblings, not as a fallback chain. The SMS is shaped by a billing limit — 160 characters per segment — so composeAlert throws away the lead's intent, urgency and the suggested opening question to fit two segments. A WhatsApp Cloud API text holds 4,096 characters, so composeWhatsapp keeps exactly the context the SMS had to drop. Reusing the 160-char shape where it does not apply would be cargo cult, which is why these are separate functions rather than one function with a flag.

The caveat is a provisioning fact, not a code problem: Meta only delivers a free-form WhatsApp message inside the 24-hour customer-service window. Outside it, an approved template is required. No amount of code papers over that, so it is stated here. Delete whichever of the two nodes a client does not want.

The code lives in src/, not in the JSON

lead-to-callback.json is generated. The Code-node bodies are built from src/*.js by build.mjs, so the functions verify.mjs tests are byte-for-byte the ones that ship inside the workflow. Editing the JSON by hand is the one thing not to do.

src/normalize.js   field mapping (incl. Meta Lead Ads envelope), E.164 phones, validity
src/qualify.js     rule scorer, JSON extraction, the clamp, the tier
src/compose.js     the SMS, the WhatsApp payload, the CRM payload, the audit row
src/prompt.js      the system prompt (advisory score, no invented facts)
build.mjs          src/*.js  ->  lead-to-callback.json
verify.mjs         149 assertions + 5 mutation tests
fixtures.json      7 leads, 9 model responses (clean, fenced, prefilled, broken, lying)
mock-endpoints.mjs stand-in Twilio + WhatsApp + GoHighLevel on :4000, real wire formats

Run it

node build.mjs          # regenerate the workflow JSON
node verify.mjs         # 149 assertions, 0 failures
node verify.mjs --all   # the above plus the 5 mutation tests

verify.mjs includes five mutation tests: it patches a copy of the relevant source file to disable one guard at a time and asserts the suite notices. Four target qualify.js (the clamp, the tier recompute, the score-range limit, the empty-summary check). The fifth targets normalize.js and restores a bug that really shipped — see below. If a guard can be deleted and the tests still pass, the guard was never tested. The harness also fails loudly if a mutation's anchor text no longer exists in its file, because a stale test that silently stops testing is worse than no test.

The email bug, and why it is in the test suite forever

The first version of the email validator was /^[^@\s]+@[^@\s.]+\.[a-z]{2,}$/i. That domain half forbids dots, so it rejected every @company.co.uk address and every subdomain address. Combined with design decision 2, the consequence was not a cosmetic validation miss: a lead who left only a .co.uk email came out the far end marked unreachable and was never contacted at all.

It was caught by a new WhatsApp test asserting the long-form alert keeps the email the SMS has no room for — the email was missing, because normalization had thrown it away. The fix allows one or more dot-separated labels before the TLD. A 14-case table test (7 accept, 7 reject) and mutation test #5 now stand on it; the mutation puts the old pattern back and asserts the suite fails.

Deliberately not RFC 5322. The only question an inbound lead form needs answered is whether the address is worth sending to, and anything this lets through that bounces bounces visibly.

The fallback was proven by accident, which is the best way

The ANTHROPIC_API_KEY in this run was dead. The API returned 401 authentication_error: invalid x-api-key. That is the real failure, unsimulated, and it is what the audit row recorded. The pipeline:

  • did not stop (onError: continueRegularOutput on the HTTP node)
  • scored the lead by rule instead — 95, tier A, correctly urgent
  • said so out loud: [scored by fallback] in the SMS, scored-rules in the CRM tags, scored_by: "fallback" and the full 401 text in the audit row

Caveat stated plainly: lead_intent and lead_urgency landed in the CRM empty, because those fields only exist if the model wrote them. The rule engine does not invent them. That is the honest cost of the degraded path, and it is visible in the record rather than papered over.

What is NOT verified yet

  • The AI path has never run green. source has only ever been observed as fallback on a live execution. The ai, ai+rules(disagreed) and out-of-range-clamp paths are covered by verify.mjs against the nine fixture responses, but not yet by a real model call. Needs a working API key.
  • Latency with a live model is unmeasured. The 2.0 s above includes a failing call plus one 1,500 ms retry wait. A successful Sonnet call will dominate that figure instead. It will not approach 60 s; it has not been timed.
  • No real Twilio, WhatsApp or GoHighLevel traffic. All three endpoints are mocks that speak the real wire formats (form-encoded for Twilio; Cloud API JSON with the recipient as digits and no leading +; GHL JSON with the Version: 2021-07-28 header). What was verified is the exact request the live APIs would receive.
  • The WhatsApp 24-hour window is untested, because a mock has no window. A free-form text only delivers if the owner messaged the business number in the last 24 hours. For an owner-alert use case that is usually fine — it is their own number — but a client who goes quiet for a day needs an approved template.

Three things that cost time and are worth knowing:

  • The workflow JSON needs a stable top-level id. Without it the n8n CLI import fails on NOT NULL constraint failed: workflow_entity.id. With it, re-importing updates this workflow instead of adding a duplicate.
  • Importing deactivates the workflow, and flipping active back does not undo that. Setting workflow_entity.active = 1 in sqlite makes the UI show the workflow as active while every POST still 404s, because the row that actually registers a production webhook lives in webhook_entity and is still empty. The sequence that works is n8n import:workflow, then n8n publish:workflow --id=leadpipe00000001, then restart n8n. Confirm with select webhookPath, method from webhook_entity; before trusting a curl.
  • If a POST returns {"message":"Workflow was started"} but nothing reaches the mock, check the n8n log for port 5678 is already in use — a second instance answers the webhook and runs a stale copy of the graph.
